# 召唤机甲技能生态调研与实施路线图

核验日期：2026 年 10 月 18 日。近期对象：机器人开发者与厂商；市场重点：中国。仓库：`D:\CodexDeploy\summon-mecha`，起始提交 `c4d2ead`，含既有未提交改动。

平台应当围绕**开发者把能力变成有适配证据的技能产品，厂商把设备变成持续获得能力的生态入口**建设。近期最有价值的资产，是“某个技能版本在某款具体机器人配置上，经过什么验证、通过什么渠道交付、结果如何”的可追溯记录。供需双方通过这份证据成交，Agent 再把交付结果反馈到供给质量。

本轮完成了代码与本地数据核验、当前官方资料调研、分阶段实施设计，以及第一项技能市场修复。机型适配矩阵、供需工作流和 Agent 新能力尚未实现，后文逐项给出边界与验收条件。

## 1 战略选择

### 先服务能创造供给的人

开发者最需要知道：支持哪个具体机型与开发版本、怎样构建与测试、审核缺什么、在哪里找到真实适配需求、自己的维护投入能否复用。厂商关心的是设备增值、开放边界、兼容性与事故责任，以及客户是否绕过其控制与支持体系。

因此建议把开发者门户组织为五个连续任务：**选择目标机型 → 准备技能 → 验证并提审 → 发布与交付 → 维护与需求响应**。保留现有商城承接交易；继续用独立开发者门户承接供给。用户明确提出开发者与厂商优先，不能继续套用旧文档中“第三方供给为零，所以暂不投入”的经营判断。

### 平台差异化

厂商已有自己的开发工具、应用分发和设备管理入口。召唤机甲的优先价值应放在：跨厂商的能力发现、适配证据、需求组织、交易授权、交付服务与长期维护。统一商业与证据口径，各厂商执行格式继续由其 SDK 与授权工具负责。

这是一项战略判断：在早期扩大“可验证、可复用的技能供给密度”，比扩大品牌目录、建设一套通用 IDE 或宣称自动跨本体转换更有积累价值。采用模块化单体与配置注册表；保留现有买断制、绑定真相源、审核闸门及人工交付边界。

### 增长指标

建议北极星为**每月被真实目标设备成功使用、且有验收证据的技能版本数**。没有实际运行证据时，只统计到人工安装自报，不能混入真机执行成功。

| 指标 | 定义与用途 |
|---|---|
| 首次发布完成率 | 已完成准入的开发者中，完成首个发布版本的人数占比；定位上架摩擦 |
| 首次发布耗时 | 从开始准备技能到具备发布条件的中位耗时；区分等待运营与技术处理 |
| 有效适配覆盖 | 技能版本、机型配置、固件、载体和验证记录组成的有效组合数；不做技能数乘机型数 |
| 需求有效匹配率 | 已通过平台评估的需求中，有符合硬性条件的供应方案的占比 |
| 交付成功率 | 按人工自报、仿真、真机执行分别统计；安装成功与业务任务成功分别统计 |
| 维护健康度 | 已发布技能的响应时长、复现成功率、受影响设备数及版本回归率 |

这些是拟采用口径，当前本地数据不足以计算真实经营结果。目标值应在第一批受邀开发者与设备试点之后校准。

### 本轮发现的近期变化

**加速进化已经形成值得直接对标的开发与分发生态。** 当前官方开发文档包含 BoosterOS Python SDK、C++ SDK、Agent 开发和发布。Agent 配置使用 `agent.toml` 与 `build.toml`，包含机型、平台、最低 API 级别、依赖和签名；机型组合受系统版本约束。平台应研究如何保留这些原生信息与签名，而不是把它们拍平成一个通用压缩包。[开发入口](https://docs.booster.tech/developer-guide/)、[配置与发布](https://docs.booster.tech/docs/developer-guide/agent-development/configuration-and-release/configuration-files-and-options/)

**SDK 版本与设备固件必须分别记录。** Booster C++ SDK 更新页列出 v1.6.3，日期为 2026-09-15，部分新接口要求固件至少 v1.8.0.9。仅凭“SDK 已升级”不能宣布设备具备新功能。[官方更新记录](https://docs.booster.tech/docs/developer-guide/cpp/changelog/)

**智元资源类型的能力限制会直接改变技能商品设计。** A3 v3.2 的资源表显示，motion 与 creative work 的能力不同于 skill；不能因为有导入导出接口就宣传所有技能都能导入。2026-09-24 更新记录还提示内置麦克风问题，并修正关节、传感器和话题说明；语音技能必须按准确软件版本验证。[资源管理](https://open.agibot.com/docs/en/aimdk/a3/v3_2/dev_guide/07-05-resource_manager)、[更新记录](https://open.agibot.com/docs/en/aimdk/a3/v3_2/dev_guide)

## 5 技能供给应怎样组织

### 一份可比较的技能产品说明

沿用现有技能版本与中立 manifest，新增能力应通过明确的兼容策略逐步接入。建议展示和审核以下信息：

| 信息 | 需要回答的问题 |
|---|---|
| 能力与业务任务 | 完成什么动作或任务，适用什么场景，哪些情况不适用 |
| 输入与结果 | 接收什么参数，返回什么结果，成功如何判断 |
| 适配目标 | 具体型号、开发版本、硬件选配、固件、SDK 与运行平台 |
| 载体与来源 | 厂商原生包或程序、精确版本、摘要、构建来源与可用交付通道 |
| 依赖与前置条件 | 地图、标定、相机、麦克风、网络、站立状态等必要条件 |
| 验证证据 | 声明、静态校验、仿真、真机分别做了什么；由谁在何时验证哪份产物 |
| 使用约束 | 场地、速度、持续时间、急停、人工监护等；不以声明替代端侧控制 |
| 商业与维护 | 买断范围、支持期限与响应方式、变更记录、已知问题与回退条件 |

其中“可交付、可适配、仅展示”继续沿用项目已有 L1/L2/L3 业务边界。验证阶段另行记录，不把 L1 机型等级与 L1 仿真审核层混为一个字段。

建议增加机型配置与技能目标关系、验证记录等加性结构；表名与迁移方案在相应实施卡确定。历史版本先展示证据缺口，新版本逐步执行严格校验，避免未经迁移直接把已有人工交付链路全部拦断。

### 开发者门户的任务导航

继续复用现有邀请、实名、协议、建技能、传包与审核功能。重点补足：选择目标机型后的开发条件说明、可验证样例、提审前检查、逐项失败原因、目标产物列表、验证报告与维护入口。

制造商优先意味着需要“组织及产品证据”的展示能力，不意味着立刻新增一套厂商登录体系、团队 RBAC、结算系统或通用 SDK CLI。这些仍按原项目立项边界处理。

## 6 需求与供给如何形成闭环

近期需求对象优先覆盖：**新技能需求、已有技能适配需求、验证与交付协作需求**。需求方可以是厂商、开发者或实际场景客户；联系信息与未公开资料只向有权限的参与方开放。

需求最少应包括目标任务、具体机型配置、运行环境、已有技能或素材、可提供的测试条件、预算范围、时间窗口及验收标准。机型未知可以提交，但应进入待评估，不能自动宣布有兼容方案。

```mermaid
flowchart LR
  A[提交需求与设备条件] --> B[平台评估与补充]
  B --> C[现成技能或适配方案]
  C --> D[开发者响应与确认范围]
  D --> E[绑定具体版本与验证计划]
  E --> F[交付和验收]
  F --> G[有授权的复用技能供给]
  F --> H[问题反馈与维护]
```

状态建议为草稿、待评估、待补充、匹配中、实施中、待验收、已完成、已关闭。提交方案不等于接单，接单不等于平台担保；付费继续复用既有订单及合同机制。本阶段不附带悬赏托管、自动分账或提现承诺。

匹配顺序应当是：先排除不满足机型、开发权限、运行依赖与交付条件的方案，再依据验证证据、任务相符程度与维护状态排序。每个结果显示匹配理由、缺口与下一步，不用一个无法解释的 AI 分数掩盖不确定性。

需求关闭前，必须保存验收条件与实际证据。定制成果能否复用、源代码与数据归属、厂商专有素材是否允许再分发，必须在项目范围确认时约定，不能默认变成公共上架资产。

## 7 平台技能 Agent 的建设方向

### 三层职责

| 层 | 职责 |
|---|---|
| AI 需求与方案层 | 澄清需求、检索有权限的技能、解释适配差距、建议下一步 |
| 平台交付与设备 Agent | 身份与授权校验、选择精确产物、下载验签、安装回退、任务状态与设备证据回报 |
| 厂商 SDK 与控制器 | 实际硬件控制、运动仲裁、实时约束与厂商规定的安全机制 |

AI 自然语言输出不能直接变成电机指令。平台 Agent 安装成功也不等于某个任务执行成功。厂商 Agent 应用包与召唤机甲设备管理 Agent 是不同概念，门户和文档要明确区分。

### 先补可观测与可判定

建议按 DID 增加受鉴权保护的设备能力快照：准确机型与配置、固件与 SDK、Agent 和适配器版本、可运行平台、资源与健康状态、已安装版本、报告时间和来源。未知值明确保留未知，健康信息显示时效，不从“在线”推断“可安全执行”。

部署前进行确定性预检查：本人授权有效、绑定未解除、版本未熔断、目标机型与产物匹配、依赖满足、适配器可用、版本升级或回退政策允许。未知条件交给明确的人工确认或阻断规则处理，不能默认为通过。

现有状态机继续负责下载、安装、失败和恢复；后续执行结果另设清晰口径。模拟器、dry run、人工确认与真实运行必须能在记录和界面中区分。

### 真机验证的触发条件

一台明确的开发版设备、合法 SDK 与载体规范、可访问的测试环境、操作者和验收任务到位后，逐个完成：身份与版本发现、预检查、精确产物下载、安装、受控运行、失败恢复、回退与证据回传。先完成一个机型配置，再扩展第二个配置；不能用一次仿真结果宣布三厂已打通。

厂商工具已经具备的能力优先通过有授权的本地 SDK 或原生包衔接。不得抓取厂商账户、绕过签名、修改厂商云或删除厂商包的完整性信息。
