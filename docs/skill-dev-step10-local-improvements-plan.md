## 4 交付补偿的业务守卫

自动补偿范围先限定为 `app` 通道的技术异常。建单时产生授权、下载前校验付款的既有规则保持；自动补偿必须同时核验已付款订单状态与对应成功支付流水。只有 processing 或 completed 状态而无匹配流水的历史手工单转人工核查，不推定已收款。

| 消费时的状态 | 处理 |
|---|---|
| pending 或 pending_payment | 等待付款，不占补偿次数，不交付 |
| processing 或 completed，且支付流水、订单和金额匹配 | 继续检查条目、授权、退款和熔断条件 |
| canceled、closed、fraud | 阻止补偿；迟到成功回调保留支付流水并告警，不恢复订单 |
| 已成功交付或 active | 跳过，不改设备、license、版本、激活次数、到期时间 |
| app 无设备，结果为 pending_bind 且 ok=true | 正常等待绑定，不能记成技术失败 |
| revoked、expired、expiring，或 expires_at 已到 | 停止，不恢复授权、不续期 |
| 试用授权 | 交由现有试用和 Deploy 流程处理 |
| 相关退款、售后申请或原生条目退款取消数量存在 | 保守停止并交人工，避免自行决定部分退款政策 |
| 技能熔断 | 停止并记录原因；解除后重新核验，不能自动重置预算 |
| Agent 缺任务、未注册通道、分类或购买依据缺失 | 配置或业务待处理，告警；不能无限技术重试 |
| 明确技术异常且以上守卫通过 | 在总预算内执行单项补偿 |

售后守卫至少覆盖申请中、审核中、已批准和已退款，以及退款请求 pending、success、failed；失败打款不能恢复已冻结授权。历史被驳回但未恢复、归属不清或原生部分退款记录均转人工核查。新建授权核验 sale 闸门；补交付同时核验下载闸门，保守阻止已熔断技能的自动恢复。

付款回调只允许 pending 或 pending_payment 推进到 processing。重复回调维持幂等，并核查未完成补偿记录。取消、关闭或风控订单的迟到成功回调需返回明确的支付回调待核查结果；不在本次自行设计自动退款。

本地 paid 流水可能由 mock 网关产生，只能证明模拟支付链路。补偿准入核对 order_id、paid 状态及订单金额，不据此声称真实到账或微信支付验收完成；生产启用仍要求现有生产安全网关守卫通过。

自助取消需进入事务，锁订单后重新判断能否取消。补偿消费与取消、售后冻结、退款、熔断的相关写入必须审查共同资源及锁顺序；仅给新 Job 加订单锁不足以证明所有竞态消失。存在无法证明安全的并发路径时，自动补偿保持关闭。

## 5 持久记录和单项执行

初次交付与补偿共用结果记录和当前授权的交付调用，返回成功、正常等待、可重试技术失败、禁止重试、需人工处理这些稳定结果。保留现有 `ok/message/data` 合同，追加稳定原因码；禁止按中文消息内容判断重试。严格的付款流水、退款和预算守卫用于补偿入口，不能把建单时产生授权误改为付款后才创建。只有明确成功才能清除旧技术失败。

监听器继续兜底捕获异常，避免触发建单重试；各技能条目分别处理，第一项失败后仍处理第二项。授权创建前失败、分类缺失和 Agent 缺任务均巡检告警，转人工处理，不进入本批自动恢复。

首批不新增表和购买快照。仅针对已有 `app` 授权，且 `meta.delivery_failed` 记录了明确异常的条目，在同一授权的 `meta.delivery_retry` 保存 state、attempts、next_retry_at、lease_token、lease_until、reason_code 和有限期派发标记。该字段是补偿预算唯一依据；队列重投、扫描、重复回调和 CLI 都不能重置它。

这份记录随授权所在事务提交或回滚。队列派发失败时，扫描可按持久记录重新派发；授权根本不存在时则无此恢复能力，必须进入缺授权巡检和人工核查。未来完整恢复缺授权，需要单独设计按订单条目的持久账本与可靠购买快照，不纳入首批。

补偿按订单、订单条目、授权的顺序加锁；每次重新读取完整 meta 后局部修改，保留下载统计等无关字段。所有会更新该授权 meta 的相关入口都要审查，包括监听器、下载计数、设备绑定和其他整体保存入口，不能让旧模型覆盖预算或租约。已有 `order_item_id` 唯一键继续兜底，但不能代替业务锁。

已有授权的版本、次数上限和到期日直接沿用，不重新查询最新 SkillVersion。失败项使用当前授权设备；成功或 active 授权跳过。补偿不调用整单 `grantForOrder()` 或 `grantForItem()`。旧 `redeliver()` 必须收敛到安全入口或停止作为生产补偿入口，避免留下绕过守卫的捷径。

付款、取消、售后、原生退款和熔断并发需分别证明：取消在订单锁内重检；售后冻结与补偿写同一授权行且最终不能恢复 revoked；原生退款的数量检查不能独自保证并发安全；熔断记录也没有现成的共同订单锁。后两项必须在 B 阶段落实共同序列化或可证明的守卫，再允许执行补偿；未通过时仅保留巡检和 CLI 检查，自动和 CLI 执行均关闭。不借此决定部分退款的授权撤销政策。

## 6 队列和恢复策略

Job 只携带授权 ID，显式 `afterCommit()`。消费者重新读库并检查全部守卫；不序列化旧订单、设备或授权状态。支付或开票回滚时，不得留下本次事务的新补偿状态或提前执行任务。

同步初试以外最多补偿3次。建议每次失败后分别等待60秒、300秒、900秒；参数放配置文件，默认关闭自动执行。第一次异常建立失败周期，随后所有入口的尝试均计入同一预算；付款回调也不能再次把它作为无限同步初试。定时扫描只派发到期、非终态记录。成功、阻止、需人工和耗尽均有明确状态及原因。

领取事务内先加锁并核验业务守卫，再原子领取记录、持久增加次数并设置执行租约。领取提交后，真正交付的本地事务重新获取锁，复核租约 token、终态和全部业务守卫，通过后才调用 AppChannel。进程中断后，租约到期才能再次领取，之前的次数不回退。落结果时再核验领取标识，旧任务不得覆盖新任务或终态结果。重复投递和 CLI 共用这一本账，队列自身重投次数不另开业务预算。

建议 Job timeout 为30秒，小于当前队列 `retry_after=90`。Windows 环境不能仅凭 timeout 参数就声称进程可被硬中断，开发时需核验运行时的超时能力；重复消费的正确性仍由数据库锁、租约和幂等守卫保证。不要通过全局修改 `after_commit` 影响其他任务。

复用 database 队列与 scheduler，不新增外部消息服务。扫描限量并设置有限期派发标记，避免 worker 暂停时每分钟重复堆入同一批任务；派发失败或未消费后，标记到期可再次派发。派发标记用于控制积压，执行租约用于保证正确性，两者不能混用。worker 恢复后不能重新获得3次预算。

次数耗尽、缺少配置或危险状态转人工时，调用 `AdminAlertService`，按条目和失败周期去重。告警附订单、条目、次数、原因码和处理命令，不附 license、下载签名、原始支付报文或数据库密码。

命令行拟提供 `skills:redeliver {orderId}`，默认只检查并输出各项状态，只有显式 `--execute` 才执行。执行也经过全部守卫和同一预算，不提供绕过支付、退款或撤销的 force。本批不增加管理后台重发按钮。

## 9 测试与证据

当前部署库不能直接用于 PHPUnit。仓库 `phpunit.xml` 未显式覆盖数据库连接，而测试会写客户、订单和技能数据；应先建独立测试库，显式注入连接并断言库名不是 `summon_mecha_local`，再跑迁移和相关测试。测试邮件使用 array，队列在普通用例中隔离，在真实 worker 集成用例中使用专用测试库。

| 验证 | 必须证明的行为 |
|---|---|
| 前端 | 首次进入、登录或注册成功与失败、退出、token 过期、返回、刷新均没有假券；页面说明和技能结算优惠码各自正确 |
| 交付结果 | ok=true 成功；无设备等待绑定正常；业务拒绝不被当技术重试；异常留痕 |
| 多条目 | 首项交付异常或授权创建前失败，后续条目仍处理；缺授权巡检告警且不自动建授权 |
| 安全守卫 | 未支付、终态订单、试用、撤销、过期、熔断、售后和各类退款均不被恢复 |
| 支付事务 | 开票失败回滚后，任务不可提前执行；迟到成功回调不恢复取消订单；回调异常可在后台看到 |
| 当前权益 | 重放不改设备、license、版本、到期日、激活状态；历史依据不足不自动补授权 |
| 预算和恢复 | 同步初试外最多3次；扫描、重复回调、CLI 不刷新预算；进程中断和重启可恢复 |
| 真实并发 | 两个 worker，加 CLI 或回调竞争，仍只有一行授权、一次有效推进、正确次数且 meta 统计不丢 |
| 告警 | 终态告警可读、按周期去重、无密钥或支付敏感报文 |

现有 `DeliveryHardeningD234Test`、付款幂等与退款边界测试、`AgentChannelS15Test`、`SkillCouponB18Test` 可作为回归起点。现有顺序幂等测试不等于并发测试。

`DatabaseTransactions` 会使提交后回调一直等到外层测试事务结束，不能用这种用例证明真实 afterCommit 行为。该部分需在隔离测试库使用真实提交及独立 worker，验证提交前读不到、回滚后不消费、提交后可恢复。

每阶段记录代码 diff、实际执行命令、测试输出、H5 截图和未通过项。已有历史测试失败需区分基线问题和本次新增问题；不得只写“全部通过”而省略失败范围。以上为方案编制时的验收要求；实际执行范围、通过证据与未做分支见实际交付说明。

## 10 回滚与停止条件

开发前把拟改文件备份到 `.claude/backup/step10-local-improvements/`，保存 Git 状态及校验值，避免覆盖当前已有的 `utils/config.js` 本地端口配置。

前端回滚只恢复本阶段页面文件并重编译 H5。后端先关闭补偿开关并停止其扫描，再等待或停止相关 worker，恢复本阶段文件并重启服务。授权 meta 的补偿和诊断记录保留供核查，不清空队列；首批无新迁移，不执行笼统的 `migrate:rollback`。开发交付时补充按实际改动生成的精确回滚命令。

出现重复授权、状态回退、设备被旧订单覆写、预算重置、退款或熔断被绕过，或无法证明并发安全，立即停用自动补偿并记录失败证据。前端清理可单独交付，后端不得带着上述问题启用。

## 11 后续三项的技术路径

激活次数通过现有 `SkillEntitlement::remainingActivations()` 派生，API 增补 activations、max_activations、remaining_activations；null 显示“不限次数”，有限次数展示已用和剩余，达到上限时与后端安装守卫一致。不新建计数来源。

下载并发专项使用独立 MySQL 库、多个连接和进程，同时请求同一授权的下载计数更新。验证成功请求对应的计数、拒绝请求不计数、并发时无丢失更新；测试脚本不能指向当前商城库。

开发者浏览器专项使用隔离测试服务、测试邮箱和一次性邀请，从客户身份进入开发者身份，检查跳转、Cookie、CSRF、重复邀请、失效邀请和入驻结果。已有 HTTP 会话测试继续保留，浏览器操作补足真实导航证据。

缺授权的完整自动恢复列为第二期：先确定购买快照和按订单条目持久记录，再设计有限恢复，避免按当前最新版本猜测历史权益。

迟到成功支付回调的资金处置、原生部分退款对应的授权政策、真正用户券包的归属与领取规则仍需业务决策。这些不阻碍先完成 A 和后端安全守卫；遇到对应记录先告警并转人工，不能由技术补偿自行决定。
