# ADR-0001：设备端 Agent 边界与标准转码器分层

## 1. 背景

外部《具身智能超级助手与云端赋能平台》蓝图提出了一套从内核隔离、进程监督、运动仲裁、技能热插拔、远程接管到多品牌适配的完整设备端系统。

该蓝图的部分工程思想有价值，但不能直接作为当前项目的生产实施方案，原因如下：

1. 当前平台定位不是机器人操作系统，不是固件/硬件厂商；设备 Agent 当前目标是安装、授权、启停、回滚、健康上报和事故闭环，不是接管机器人实时运动安全。
2. 当前平台侧 Agent 契约、设备真相源、签名下载、部署状态机和安装记录已经存在；外部蓝图没有复用这些能力。
3. 外部蓝图自创 `.rsp` 技能运行时格式，与 D5“不自创技能包格式，使用中立 manifest + 厂商导入适配器”冲突。
4. 外部蓝图的 AST 黑名单、`exec()` 热加载不是安全沙盒，不能满足第三方技能隔离要求。
5. 外部蓝图的智元/ROS 2 适配器是桩实现，宇树真机导航和遥测仍使用仿真状态，不能作为真机交付依据。
6. 当前仓库的 `skill_build` 只有构建意图与登记，`BuildResult::success()` 没有实际生产者，`skill_build` 尚未进入交付链路；这意味着“一次上传、多机型下发”目前不成立。

## 2. 需要决策的问题

本次 ADR 要冻结四个问题：

1. 设备端 Agent 是否负责在机器人上现场转码技能？
2. 标准转码器属于平台还是设备端？
3. `.rsp` 是否能成为新的技能包格式？
4. 平台是否可以自己承担实时运动仲裁和远程接管？

## 3. 决策

### D-A1：Agent 是设备侧发布管理器，不是机器人操作系统

Agent 的核心职责固定为：

- 设备注册、配对和身份认证；
- 心跳、能力快照和健康上报；
- 领取平台任务；
- 下载并验证签名、哈希和任务参数；
- 调用厂商插件安装、启用、停用、卸载、回滚和回收；
- 回报任务状态、错误码和安装事实；
- 执行平台下发的、经过签名的熔断指令；
- 保留离线任务和授权状态，等待下次上线继续执行。

Agent **不在设备上做以下事情**：

- 不解析、重定向或重新生成通用动作数据；
- 不把中立技能现场编译成厂商包；
- 不直接仲裁关节、步态、平衡或运动安全；
- 不替代厂商运控控制器；
- 不实现远程摇杆、LiveKit 视频接管或硬件急停；
- 不自行推断“设备支持某技能”。

设备上位机或厂商控制器仍是运动安全的唯一责任方。Agent 只调用厂商允许的高层安装、启停和高层动作能力。

### D-A2：标准转码器是平台侧离线构建能力

标准转码器定义为平台侧独立的、异步的、可复现的构建服务，不是 Laravel Web 请求内的同步逻辑，也不是设备端运行时组件。

职责是：

1. 读取中立技能包和源文件；
2. 解析目标机型资料 `target_profile`；
3. 调用对应 `CarrierBuilder`；
4. 生成目标机型载体；
5. 执行结构、安全、兼容性和可复现性检查；
6. 将产物写入 `skill_assets`；
7. 将构建事实写入 `skill_build` / 构建运行记录；
8. 交由现有审核、上架和下发系统消费。

标准转码器只产出经过审核的**不可变成品**。Agent 必须按字节原样安装，不得在设备上二次打包。

### D-A3：技能包格式保持中立 manifest，拒绝 `.rsp`

继续使用：

```text
zhaohuan.skill/v2
manifest.json
```

以及现有 `carrier_type` 词表：

```text
file / cloud_config / remote_service / api_bundle
motion_data / app_package / vendor_package
```

外部蓝图中的 `.rsp + workflow.py` 不能成为新的事实标准。若未来需要承载可执行技能逻辑，应作为 `app_package` 或 `vendor_package` 的内部载体，并继续在外层使用中立 manifest，禁止绕过现有清单、权限、风险和兼容性字段。

### D-A4：Agent 下发只接受“构建成功且可追溯”的成品载体

对 `agent` 通道，创建/执行下发任务前必须同时满足：

1. `skill_build.status = success`；
2. `skill_build.artifact_asset_id` 指向真实存在的 `skill_assets` 记录；
3. 产物 `file_hash` 与构建记录一致；
4. 目标 `model_code` 与构建记录一致；
5. 技能已过审核且允许 `agent` 通道；
6. 设备绑定、授权、固件和 Agent 版本检查通过；
7. 包签名和 `deploy_task` 签名有效。

对 `manual` 通道，继续保留现有下载 + 人工安装闭环。手工通道可以接受经过审核的上传产物，但不得因此宣称已达到 Agent 自动下发或 L1 可交付。

### D-A5：设备端只安装不可变成品，不做运行时转码

设备端安装事务固定为：

```text
收到任务
-> 下载
-> 验证任务签名
-> 验证 SHA-256
-> 解包安全预检
-> 暂存到独立 staging
-> 检查目标机型/固件/SDK
-> 调用厂商插件安装
-> 健康检查
-> 原子提交
-> 上报安装事实
```

失败时必须保持旧版本可恢复；不得出现“平台认为安装成功，但设备实际未安装”的假成功。

### D-A6：实时运动仲裁、远程接管和 LiveKit 另行立项

以下能力不随本次 Agent/标准转码器建设自动获批：

- 平台直接控制底盘速度；
- 平台仲裁 P0/P1/P2/P3 运动指令；
- 平台替代厂商 ZMP、平衡和急停逻辑；
- 实时远程摇杆；
- LiveKit 音视频接管；
- 多品牌“零改动”运动控制。

如业务确实需要，必须另立 ADR，重新评估安全责任、厂商 EULA、保险、隐私、数据出境、HIL 和真机急停方案。

### D-A7：跨品牌承诺必须由构建产物和 HIL 证据共同支撑

兼容性承诺维持 L1/L2/L3：

- **L1 可交付**：存在目标机型构建成功的载体，且该机型完成相应 HIL/吊架验证；
- **L2 可适配**：有可转换来源，但没有目标机型成品，仅承诺“可转换”；
- **L3 仅展示**：没有可用构建路径或验证证据。

“主框架零改动”“统一适配器”只能描述接口设计，不能替代每个厂商的插件实现和 HIL 证据。

## 4. 方案对比

### 方案 A：平台离线转码 + 设备只安装成品（采纳）

优点：

- 产物可复现、可审计、可签名；
- 审核的是最终字节，不是临时生成结果；
- 设备端故障面最小；
- 回滚和事故追溯简单；
- 不越过厂商运动安全责任边界；
- 与现有 `skill_build`、`skill_assets`、`deploy_task` 方向一致。

代价：

- 需要新增独立构建面；
- 需要目标机型 profile 和构建环境治理；
- 一次上传多机型不是“免费获得”，需要算法、工具链和验证成本。

### 方案 B：设备端现场转码（否决）

否决原因：不可复现、难以审计、设备算力不稳定、构建失败直接影响交付、无法保证审核产物等于安装产物，且会把设备 Agent 变成未经批准的运行时编译器。

### 方案 C：平台接管实时运控（暂缓）

该方案会把项目推进到机器人操作系统和安全关键系统层级，超出本次决策范围。没有新的 ADR、责任边界和 HIL 结论前，不得实施。

### 方案 D：沿用 `.rsp` 自定义运行时（否决）

否决原因：违反 D5，绕过现有 manifest、权限、风险、兼容性和审核链路，并与现有 `skill_assets`/`skill_build` 模型重复。

## 5. 结果与影响

### 正面影响

- Agent 的职责可以被单独验收；
- 标准转码器不依赖真机即可开发和测试；
- 所有技能产物都具备来源、构建器版本、目标机型、哈希和审核记录；
- 下发任务可以在创建前阻断“无产物/错机型/旧构建/未审核”；
- 真机验证范围可以收敛到一个机型、一个固件、一个 SDK 版本。

### 负面影响

- 增加平台构建队列、构建 worker、存储和工具链维护成本；
- 需要定义并维护目标机型 profile；
- 自动动作转码需要算法质量和安全验证，不能靠接口声明完成；
- 在真实构建器接入前，`skill_build` 仍需要明确的 pending/failed 语义，不能假装成功。

### 必须保留的诚实边界

- 当前唯一已跑通的生产交付通道仍是手动安装；
- 没有真机/HIL 时，不能对外宣称 M4 完成；
- 没有目标机型产物时，不能把 L2/L3 宣传成 L1；
- 没有真实构建器时，不能把 `skill_build` 的 pending 改写成 success。

## 6. 实施约束

1. 不改写现有 manifest schema；标准转码器必须消费现有 `zhaohuan.skill/v2`。
2. 不在设备端存放构建工具链、源代码或通用动作重定向算法。
3. 不在 Web 请求线程里执行动作重定向、Docker 构建或大文件打包。
4. 不让构建 worker 直接使用无限网络；依赖必须预装或通过白名单镜像获取。
5. 构建产物必须不可变；同一构建键重复执行应返回同一产物或明确失败。
6. Agent 必须验证任务签名、包 SHA-256、目标机型、授权、版本和防降级条件。
7. 安装事务必须支持中断恢复、旧版本保留和回滚。
8. 构建、审核、上架、下发和安装都要有可追踪 ID。
9. 任何 `success` 必须能被真实产物、真实安装记录或 HIL 证据验证。

## 7. 验收门槛

### 决策门槛

- 项目负责人确认 Agent 只负责发布管理和厂商插件调用；
- 确认标准转码器属于平台离线构建面；
- 确认 `.rsp` 不进入正式格式；
- 确认实时运动仲裁和远程接管不在本次范围。

### 功能门槛

- 中立 manifest 校验通过；
- 一个目标机型 profile 可被构建器读取；
- 一个真实或受控的 `CarrierBuilder` 能产出 `skill_assets`；
- `skill_build` 能记录 source/build/target/output/hash/version；
- 构建失败的技能无法创建 Agent 下发任务；
- Agent 能完成下载、验签、安装、回报和回滚；
- 设备能力不匹配时，任务在下发前被拦截。

### 安全门槛

- 包签名/哈希错误必须拒绝；
- ZIP 路径穿越、符号链接、体积炸弹和非法文件必须拒绝；
- 构建 worker 与 Web 服务隔离；
- 第三方技能不能直接访问宿主机文件系统、网络和设备控制接口；
- 构建器版本和工具链版本必须可追溯。

### 真机门槛

- 在一个指定机型、固件和 SDK 版本上完成 HIL；
- 验证断网、断电、磁盘不足、错误签名、错误机型、安装中断和回滚；
- 验证厂商运控仍是运动安全的最终控制者；
- 没有 HIL 证据时，只能标为实验室/SIL，不得标为生产 L1。

## 8. 回滚策略

文档层面按以下顺序回退：

1. 停止新构建任务；
2. 将 `skill_build` 置为 failed/pending，禁止新 Agent 下发；
3. 保留已有 `skill_assets` 和历史构建记录，不删除证据；
4. 关闭 `agent` 通道的自动下发开关；
5. 回退到 manual 通道；
6. 对已安装设备执行平台既有 kill switch，等待设备上线时处理；
7. 修复构建器或 profile 后重新构建，不复用失败产物。

## 9. 后续 ADR

本 ADR 通过后，仍需要以下独立决策：

- ADR-0002：Agent 实现语言、进程隔离和厂商插件通信协议；
- ADR-0003：动作重定向算法与目标机型 profile 格式；
- ADR-0004：远程接管和 LiveKit 的产品/安全边界；
- ADR-0005：生产密钥轮换、KMS/HSM 和多公钥验签。

## 10. 决策摘要

**采纳：平台离线标准转码 + 设备端安装/生命周期 Agent。**

**拒绝：设备端运行时转码、`.rsp` 自定义格式、平台直接接管实时运动安全。**

**暂缓：远程接管、LiveKit、多品牌实时控制。**
