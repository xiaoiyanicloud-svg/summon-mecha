## 0. 总判

## 2. 四角色核心发现

### 2.1 架构师（逐行对照代码）

**事实性错误（照文档写会报错）**
- 🔴 `skill_assets.carrier_type`：计划写 `agent_package/manual_package`，**代码实际是 `file/cloud_config/remote_service/api_bundle`**（`SkillAsset.php:38`，`SkillAdminController.php:99` 硬校验）→ 计划里的载体落不了库。
- 🔴 `license_mode='perpetual'` 不在 v1 枚举（合法值 `per_device/per_order/per_account/unlimited`）；且 `pricing_mode`/`license_mode`/`perpetual` 三概念重叠。
- 🟠 `app → manual` 改名是**真实数据迁移**（存量 `skill_entitlements.delivery_channel='app'` + `AppChannel::key()` + `SkillDeliveryManager::label()` 三处）。
- 🟠 同库三个 "channel" 列；`vendor` 通道在四张表里四种写法。

**架构决策**
- 🔴 **双设备真相源**：`devices`(v1 全部接口按它鉴权) vs `device_binding`(计划新增)，`bind_status` 枚举还不一致 → 换机/转移时**可能越权读到别人付费包**。→ 选定 binding 为唯一真相源。
- 🟠 表数自相矛盾：自称 15 张，**实读约 37 张新表**（触及 51 张）。
- 🟠 `skill_entitlements` 无 `(status,expires_at)` 索引，试用回收靠 JSON 过滤 → MySQL 5.7 每分钟全表扫。
- 🟠 MQTT **QoS1 = 至少一次**，状态机**无去重/乱序处理**；试用回收**无幂等键** → 重复任务。
- 🟠 熔断 kill switch 全量下发**无分批/限流** → 雪崩点。
- 🟠 `internal.key` 静态单密钥**被复用为 Go 通道**；RSA 私钥管理缺位。
- 🟠 MySQL 5.7 **2023-10 已 EOL**；无 ES，JSON 不能索引 → 搜索需物化 `skill_search_index` 表（体检建议了，v3.2 漏了）。
- 🟠 开发者门户跨端 token：小程序 `web-view` 与独立域**不同 origin**，token 拼 URL 会泄进 referer/网关日志 → 需一次性 code 换 token。

### 2.2 市场师

- 🔴 **最大结构性错误：无视已有的租赁客户**。平台已跑 ToB 租赁（28 场景、多机合单、`from=scene`），**这就是第一方需求侧**。技能应打包进租赁套餐，双边冷启动在**第一阶段被消解**，而不是靠"填货架"糊弄。北极星应改为**"每个租赁订单里被触发的技能次数"**（价值指标），不是"可下发技能数×机型数"（库存指标）。
- 🔴 **定位缺失**：全文没有价值主张、没有 ICP。唯一讲出来的差异化（跨品牌）被 §4.4.3 自己诚实边界削掉大半。
- 🔴 **抽成 10% 在"宇树免费+你无流量无硬件"下毫无竞争力**；首年应 **0% 抽成 + 平台补贴**。买断制**收入不循环、成本循环**。
- 🔴 **需求侧不成立**：机器人装机量小、"70% 还在演戏"、无人收费。买家真实付费意愿只能来自 **ToB 场景**（租机器人办事，事需要技能）。
- 🟠 护城河不在"技能商店"（OEM 有设备就有入口），在**线下场景客户关系 + 技能+交付+现场服务**。

### 2.3 合规师

- 🔴 **B1 二清**（见阻断项）。
- 🔴 **B2 AI 备案四件套**（见阻断项）；拟人化办法令第 21 号 2026-07-15 已施行。
- 🔴 **B6 等保/EDI/小程序备案**（见阻断项）。
- 🔴 **数据合规**：`permissions:[camera]` 采集音视频/面容 = **敏感个人信息**（需单独同意+PIA）；**路人（第三人）信息**无法取得同意 → 须端侧处理/去标识；接海外厂商或用境外 LLM = **数据出境**。
- 🔴 **物理安全责任（§4.14 法律效力评估）**：三层模型工程好，但**对第三人近乎无效**——**被机器人撞伤的路人既没签承诺也没勾选**。L3 用户勾选只对本人有减责，且作格式条款免除自身责任**可能无效**（《民法典》496-497）。平台在自营时**可能被认定"销售者"（无过错责任）**。
- 🟠 内容安全缺**人工审核编制**、缺**拉黑滥用用户**、缺**未成年人保护**（大额充值退款、未成年人模式）。
- 🟠 责任保险：机器人责任险国内仍在起步，**high 风险技能应"无保险不上架"**。

### 2.4 产品 / 运营 / 财务

- 🔴 **过度设计**：≈28 张新表 + 40+ 模块，服务一个 **41 单真实订单**的平台。MVP 应砍到 **6–8 张表、1 条通道**。
- 🔴 **P0 建开发者门户是空中楼阁**：结算在 P1，P0 开发者无法变现；冷启动第一步（自营）**不需要开发者**。→ 门户应 P1/P2，P0 用 Admin 自助上架自营。
- 🔴 **全文没有人**：没有人力模型/SLA/24-7 事故通道。P0 至少 **4–5 FTE**（2–3 工程 + 1 运营/审核 + 创始人兼财务法务 + 外聘法律）。
- 🔴 **单位经济**：客服/审核是物理安装故障，**需工程师而非客服**；"会物理执行的技能"人工审核边际可能为负。估算 1000 活跃用户下**平台不赚钱**。
- 🔴 **现金流三坑（与合规 B1 呼应）**：小程序虚拟商品 iOS 端不能买、二清、发票税负压平台。
- 🟠 排期：外部审批是**月级**且串在关键路径（无支付=不可售），"并行"抹不掉。

## 3. 跨角色共识

1. **过度设计**——架构（表数差 2 倍）、产品（28 表/41 单）、市场（没必要先建三端）三方独立得出同一结论。
2. **"付费"这个前提没人验证，全计划却建立在它之上**——市场、产品、财务都点了，且文档 §10 自己承认"押注非对标"。
3. **支付/资金合规被严重低估**——合规（二清）、财务（虚拟商品+发票税）同时命中。
4. **开发者端 P0 不该建**——产品、市场都判它"没有成交对象"。
5. **缺"人"**——产品/运营/财务点名，其余角色默认无运营兜底。

**分歧（需你定）**：架构师认为"产品范围可照走、先做三件技术前置"；市场/产品认为"**先验证需求、大幅收缩 MVP，别开工**"。二者不冲突，是**先验证后建设**的顺序问题。

## 4. 修正后的建议路线

**第 0 步（不写代码，1–2 周）——把"押注"变"数据"**
- 用 2–3 个自营技能挂进现有租赁套餐加价，**向现有 B 端租赁客户**跑付费意愿实验（目标：30 天 20 单）。
- 同步启动外部审批（月级）：微信支付（商户+类目+**收付通/分账**）、**EDI 许可**、小程序 ICP 备案、门户域名备案、（若涉 AI 生成）三层备案。
- **技术前置三件**（架构师）：冻结「交付术语表」；选定「设备唯一真相源=binding」；接入 Redis+queue+scheduler。

**第 1 步 · 可售 MVP（4–6 周，仅 `manual` 通道）**
自营技能 · 手动通道（下载+人工）· 收款（或过渡对公）· 售后政策 · 基础搜索 · 评价接入。**表 ≤8 张**。

**第 2 步 · 条件触发**
- 开发者门户（P1/P2）：**有 3–5 个真实外部开发者且结算已通**再建。
- EMQX/Go/Agent 下发层（P2）：**有真机愿装 Agent** 再启动。
- 熔断/事故闭环/责任保险：随第一批"会物理执行"的技能一起上（**保险是硬门槛**）。
