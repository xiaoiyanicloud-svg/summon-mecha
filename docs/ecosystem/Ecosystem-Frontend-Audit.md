## 4. 给总方案的前端落地建议（待规划批准，未开发）

### 4.1 先建立真实数据与状态合同

1. 生产赛事/资讯数据初始为空。请求成功为空必须进入empty，失败进入error+重试。只有经过运营验证的真实内容进入正式列表。演示fixture放开发/测试环境，绝不可参与正式报名。
2. 每个赛事必须具备稳定ID、可分享地址、发布状态、更新时间、主办主体、时间/时区、活动类型和来源；报名入口读取服务端`can_register`与稳定reason，避免把活动进行状态等同报名窗口。
3. 热度、人数、奖金、报名条数、队伍数、审核通过人数分别命名；没有可追溯统计口径的数值不展示。无上限/未知不能渲染为0。沙龙/展览应显示人数/席位，竞赛才显示队伍。
4. 内容必须有稳定ID、标题、摘要、正文、来源/作者、发布时间、更新时间、封面及媒体说明、审核/发布状态。机构“官方”徽章必须来自认证主体数据，不能由卡片文本自称。
5. 以现有Bagisto/uni-app模块为基础；前端只消费审核发布后的契约，不从当前最新商品、固定赛事ID或静态文案猜测历史内容。

### 4.3 目标交互状态机

赛事详情状态与报名状态分开：

- 内容：loading → published / not-found / withdrawn / error。
- 活动：upcoming / ongoing / ended / canceled，由服务端事实和时间共同解释。
- 报名动作：not-open / open / submitting / accepted-or-pending-review / full-or-waitlist / closed / canceled / recoverable-error。
- 用户记录：未报名、已提交待审核、通过、驳回、用户取消、活动取消、（未来付费）待支付/已支付/退款中/已退款；这些目标状态必须先有真实后端持久事实再展示。

详情刷新不能把已提交者恢复为“立即报名”；容量/截止在提交瞬间仍须后端重检，前端disabled不是业务锁。内容下架不应自动抹掉用户历史报名凭据，显示方式与可见字段须有政策。

### 4.4 需要后端先确认的API合同

前端现有只有`eventApi.getEvents()`和`register()`两个方法。后端另外**已存在**GET `/api/events/{id}`（`my-bagisto-store/packages/Webkul/Shop/src/Routes/api.php:129`、`Http/Controllers/API/EventController.php:27–35`），前端应新增包装后复用，不能重复设计另一个详情端点。以下其余为目标能力，不是已有API声明：

- 列表参数与meta分页、可选筛选、更新时间；前端对不匹配DTO报错，不能静默保留示例。
- ID详情及报名schema、规则版本、`registration_open_at/close_at`、`starts_at/ends_at`与时区；详情不带他人手机号。
- 创建报名的幂等键、稳定报名ID、状态、重复提交语义、容量冲突/关闭/规则变更reason；手机号、团队、赛项唯一性由业务政策确定，不能仅凭前端推定。
- 我的报名和详情/取消/查询超时结果；游客和登录用户的归属证据、认领机制。
- 内容列表/详情的发布过滤、机构认证与来源信息；收藏/互动必须有持久接口与审核能力后启用。
- 分享仅包含公开可见ID和URL；报名凭据、手机号、登录token不能进入公共分享参数。

### 4.5 有意义的验收矩阵

| 维度 | 必须覆盖 |
