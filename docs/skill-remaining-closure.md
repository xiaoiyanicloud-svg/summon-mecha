### ✅ 本轮（2026-10-15）· 剩余批次收口

四个批次（3 剩余 / 4 / 5 / 6）一次性收口。做法上**先评审后动手**：写代码之前让四个
独立视角（越权 / 诚实 / 回归 / 过度设计）各自读真实代码攻击了一遍设计方案，**37 条结论**。
下面三件事是评审直接改变的结果，也是本轮真正值钱的部分。

#### 1 · 拆掉一条**反向失真**：平台在说"我没统计下载"，而它统计了

`notConnected()`（运营总览的"未接入"清单）里原有一条：

> 下载量 —— `skill_search_index` 是孤儿物化表，全仓无写入方 —— **做出来永远是 0**

**前半句是真的，后半句是假的。** `SkillController::download()` 每完成一次鉴权下载，
都会把 `skill_entitlements.meta.download_count` 加一；库里实测**已有 3 条记录、累计 3 次下载**。

后果与"把没统计的显示成 0"**一样坏，只是方向相反**：有人会为此立项去补一个根本
不需要补的埋点；而开发者问"我的技能被下载过几次"，得到的回答是"平台没统计"。

> 这一条比它看上去更值得记：平台的铁律一直是「没查 ≠ 合规」「未接入不能显示成 0」，
> 但**没人防过反方向**。而反方向更隐蔽 —— **没有人会去怀疑一句"我们没统计"**。
> 现在下载量是真实指标，口径写明真实边界（**只覆盖 App/API 鉴权下载，人工送达不计**），
> 并有一条行为级测试（造一行下载 → 数字必须跟着动）。

#### 2 · 一个"第二次查询必然查空"的陷阱（在本项目的地基里）

新增 `GET /api/cms/pages/{slug}` 时，我第一版照抄了原生 `PageController::view()` 的写法
（`$this->pageRepository->whereHas(...)->whereTranslation(...)->first()`）。
测试红在**第二次**请求上，且与查哪一页无关。把 SQL 打出来才看清：

```sql
-- 第二次请求的真实 SQL（bindings: [1,"terms-of-use", 1,"privacy-policy"]）
select * from cms_pages
 where exists (…channels… id = ?) and exists (…cms_page_translations… url_key = ?)
   and exists (…channels… id = ?) and exists (…cms_page_translations… url_key = ?)
```

**仓储实例把上一次的查询条件留在了自己身上** —— 两条 `url_key` 同时成立，无解，必然 404。

线上碰不到（每个 HTTP 请求各自新建容器），但**测试、队列 worker、常驻进程里会碰到**，
而且现象是"第二次查任何一页都 404"，极难定位。已改为 `Page::query()` 直查，
并把陷阱**写在控制器类注释里**（附上面这段 SQL），免得下一个人再照抄原生那条路。
原生 `PageController` 未改动 —— 那属于 Bagisto 本体，单请求容器下无碍，
动不动得单独决策，**先记录在案**。

#### 3 · 一条闪红的测试（比稳定失败更坏的那种）

`DeviceOnlineTest`「窗口边界」用 **89 秒**造"应当在线"的那台，而窗口是 **90 秒** ——
从造数据到发 HTTP 断言只要超过 1 秒，断言就随机失败。**"随机失败"比"稳定失败"更糟**：
它会让真正的回归淹没在噪声里（这正是 [skill-test-baseline.md](./skill-test-baseline.md)
开篇讲的那件事）。已冻结时间修掉，边界仍取最贴近窗口的 89/91 秒。

#### 2 · ⚠ 一个静默陷阱：**维护模式会让 worker 拒收任务**

`storage/framework/down` 存在时，`php artisan queue:work --once` **睡一觉后正常退出**
（退出码 0、零输出、一条都不消费）。而 HTTP 侧可能完全正常 —— 于是
"网站好的、队列没在跑"这种自相矛盾的状态可以长期存在。

本次排查绕了远路才定位到它（先怀疑了连接、队列名、参数、后台进程的 cwd，全不是）。
已写进运行手册 §2.6。

#### 3 · 新增可复用的验证工具

- `php artisan ops:queue-probe` —— 投一个合成任务并等它被消费。
  **退出码 0 = 有 worker，1 = 没有**，可直接进监控/部署脚本。
  `jobs` 表条数证明不了任何事（0 条既可能是消费完了、也可能是从来没进来过）。
- 实测：投递 → 1 秒内被消费，worker pid 对得上。

**首个支付测试立刻抓出一个真 bug**：mock 的 `out_trade_no` 是 `MOCK{YmdHis}{id}`（无分隔符），
而回调用 `preg_match('/(\d+)$/')` 反查订单 —— 结尾那串数字是"时间戳+id"黏在一起，
取出来是天文数字 → **永远 404**。也就是说"D5 Mock 全链路已通"这条说法**从未被跑通过**
（库里 0 张 processing 订单、全仓 0 支付测试，与之一致）。
更糟的是那个正则本身很危险：换成任何结尾带数字的真实商户订单号，都能被编出一个
看起来合法的订单 id —— 而回调接口不挂鉴权。现已改为**按网关自己声明的格式严格解析**，
解析不出就返回 null，不猜。

**严重事故即时告警**（仓库自己承认的缺口）：`bootstrap/app.php` 的调度注释里写着
"真的需要分钟级响应的是严重事故 —— 那靠的是事故一上报就有即时通知（见后续待办）"，
但"待办"底下当时什么都没接。现在严重/重大事故**在报案那一刻**就通知在岗管理员
（`IncidentService::alertIfEscalated()`，去重键与轮询命令**刻意不同**：
"刚发生"与"过了时限还没人处理"是两件事，不该互相压制）。
告警失败会让报案失败吗？**不会** —— 报案人已经出过一次事了，不能因为平台内部通知写不进去让他再报一遍。

### ✅ 设备在线读时统一（本轮 · 2026-10-14）

`device_binding.online_status` 全仓**只有四处写它，每一处都写 `true`，没有任何地方写 `false`**
（`AgentController` 的握手/配对/心跳/取指令）。也就是说**一台三个月前就断线的设备，这一列至今写着"在线"**。

而它有**五个**读点（评审只列出四个，第五个是我核出来的）：

| 读点 | 改之前 | 改之后 |
|---|---|---|
| 我的设备（`DeviceController`） | 读粘滞列 | `isOnlineNow()` |
| 我的技能里的设备（`SkillController`） | 读粘滞列 | `isOnlineNow()` |
| 运营总览「在线设备数」（`OpsMetricsService`） | 读粘滞列 → 统计的是"曾经连过"的设备总数 | `scopeOnlineNow()` |
| 模拟网关（`MockAgentGateway`） | 读粘滞列 | `scopeOnlineNow()` |
| **兼容性校验（`CompatibilityService`）** | **硬编码 `return false`** —— 注释理由是"binding 未接在线心跳"，而心跳早就接了 → 界面**恒定**告诉用户"设备当前离线" | `$binding?->isOnlineNow()` |
| 轮询网关（`HttpPollAgentGateway`） | 自己写了一份 90 秒窗口 | 统一到 `DeviceBinding::ONLINE_WINDOW_SECONDS` |

**两套判据必然不一致**：同一台设备，"界面说在线、下发说离线"（或反过来）。
现已统一到 `DeviceBinding` 一处（常量 + 单条 `isOnlineNow()` + 集合 `scopeOnlineNow()`）。

**连带修正的行为**（这是好事）：下发链路本来就用 `isOnline()` 决定挂起（`pending_online`），
现在它读的是真实心跳 —— 给一台 90 秒没轮询的设备下发，会**如实挂起**而不是标成"已下发"等着永远没人取。
（取指令接口同时返回 `dispatching` 与 `pending_online`，所以任务不会卡死。）

**刻意不动的一处**：`IncidentService::traceFor()` 里的 `binding.online_status` **保持原样冻结**。
快照的契约是"记下当时库里写的是什么"，不是"现在是什么"。真信号（`last_online_at`）就在同一份快照里并排放着 ——
**平台不替历史下结论**。这条现在有测试锁着，免得将来被谁"顺手修好"。

**为什么数据看板并进总览页、不新开页面**：设计阶段做了四视角对抗评审，其中"过度设计"
视角的论证成立且被采纳 —— 0 个开发者时，一个独立看板页对**每个**访问者的差分价值

成本是它的几分之一，且没有新增任何需要长期维护的入口。

**为什么团队 RBAC 缓做（三条独立证据，缺一条都还值得再议）**：

1. **消费者的数量是 0**：`sellers` / `developer_profile` / `developer_team_member`
   三张表**全为 0 行**。唯一存在的角色是 `owner`（入驻时自动建的那一行），
   而 owner 的能力是 `*` —— 能力校验对今天唯一存在的角色**恒通过**，等于没挂。
2. **项目自己的红线**：`CLAUDE.md` 写着「当前阶段是自营 + 客户需求两方在先（第三方开发者目前为 0），
   **不要为不存在的供给方设计功能**」，并把"第三方开发者"与微信支付资质、真机 Agent
   一起列为「**一律不排期**」。建整套 RBAC 与这条直接冲突。
3. **评审抓出一个真设计缺陷，而且我原来的方案里带着它**：按原设计，
   成员行由发起方"按邮箱"**单边写入**且默认 `status=active`，同时身份解析遇多命中**整个门户硬拒**。
   合起来就是一个**跨租户锁死工具** —— 任何人注册一个开发者主体（owner 自带 `team.manage`），
   把别人邮箱加进自己的团队，对方只要同时属于两个团队就会被全量拒绝进不了门户，
   而他自己没有 `team.manage`，删不掉那一行。**锁测试会把这个缺陷固化下来。**
   正确形态是"待确认成员行 + 被添加方站内接受 + 本人可退出"，
   这是一套需要重新设计的东西，不是给现有方案补几行。
