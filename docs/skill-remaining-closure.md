### ✅ 批次 0 · 拆掉的"会说谎"的东西（2026-10-14）

这一批的共同特征：**不崩溃、不报错、页面照常显示 —— 显示的是错误的结论**。
三份独立评审的结论在这一点上完全一致，而**三份都没有把它排进自己的批次**
（其中一份甚至判定"3B 已全部完成，仅剩提交"）。全部零外部依赖、小时级可修。

| 项 | 原本会怎样 | 现在 |
|---|---|---|
| **支付网关在生产可直接用** | `PaymentManager` 无任何环境判断；`.env` 不设 `PAYMENT_GATEWAY` 时 mock 就是默认网关，而 mock 的"支付成功"由回调参数 `mock_paid=1` **自报**，回调路由**不挂鉴权** → 生产上任何人 POST 一下就能把订单翻成已支付并发授权。而 `config/payment_gateways.php` 还写着"已按 env 兜底" | 注册表登记 `production_safe`（**允许列表**：没显式声明为 true 的一律拒绝），`PaymentManager` 执行期拒绝。**mock 与 wechat 现在都是 false** —— 因为这就是事实：此刻的生产环境拒收一切支付 |
| **备案台账能产出无号"已备案"** | `filing_no` 是无条件 `nullable`。一次提交（或一次 PUT）就能造出"已备案但不知道备案号"的记录，而到期提醒、合规判断全读这个字段 | `required_if:status,filed`。**没有号的记录不许标成已备案**；"审批中/被驳回"不带号仍合法（本来就没拿到号） |
| **机器通道能伪造审核人** | `POST /api/skill-supply/versions/{id}/review` 的 `auditor_id` **取自请求体**。internal.key 是单一平台共享密钥、不代表任何具体的人 → 写谁就是谁。而 Admin 审核台把它渲染成 `#<id>`，看上去就是"某位真人审过这一版"。出事要复盘"谁放行的"，拿到的是一个可以随便填的数字 | 该通道**明确拒收** `auditor_id`（422 + 说明该改去哪里）。于是确立不变量：**`auditor_id` 非空 ⟺ 由平台控制台以登录身份写入**。Admin 详情页两种来源改成了措辞不同的两句话 |
| **"隐私政策"页在输出安装器占位文案** | `/page/privacy-policy` **公开可达、HTTP 200、正文非空**，正文是 Bagisto 安装器的 `隱私政策頁面內容`。一个标题写着《隐私政策》的页面"有内容"，会让"这个平台有没有隐私政策"得到**错误答案** | 换成明确写"正文尚未定稿、需律师定稿"的说明（不编条款，也不留像条款的空壳）。**按全表扫描断言**，将来安装器新增页面也会被这条测试抓到 |
| **原生 Dashboard 的 ¥0.00 会被读成"没生意"** | 「总销售额」实际算的是 `已开票金额 − 已退款`（`Admin/Helpers/Reporting/Sale.php:169`）。库里 0 张发票 + 20 张未付订单 → 数字没错、含义全错 | 页面**数字之前**加口径说明，点明"未付款、未开票的订单不计入 —— ¥0 不等于没有订单"，并指向运营总览 |
| **结论型默认值** | `reconciliation.status` 默认 `matched`（已平）—— 对账还没做就写着已平（上一轮已修）。同类清扫又抓到 `skill_review.status` 默认 `visible`——**内容安全还没跑，用户评价就对外可见** | 改成 `pending` + **行为级**测试（插一行、不给值，看落库是什么）+ 表结构断言防回退。顺带把已查过确认没问题的同类列记在测试文件里，省得下次重新怀疑一遍 |

**首个支付测试立刻抓出一个真 bug**：mock 的 `out_trade_no` 是 `MOCK{YmdHis}{id}`（无分隔符），
而回调用 `preg_match('/(\d+)$/')` 反查订单 —— 结尾那串数字是"时间戳+id"黏在一起，
取出来是天文数字 → **永远 404**。也就是说"D5 Mock 全链路已通"这条说法**从未被跑通过**
（库里 0 张 processing 订单、全仓 0 支付测试，与之一致）。
更糟的是那个正则本身很危险：换成任何结尾带数字的真实商户订单号，都能被编出一个
看起来合法的订单 id —— 而回调接口不挂鉴权。现已改为**按网关自己声明的格式严格解析**，
解析不出就返回 null，不猜。

**严重事故即时告警**（仓库自己承认的缺口）：`bootstrap/app.php` 的调度注释里写着
"真的需要分钟级响应的是严重事故 —— 那靠的是事故一上报就有即时通知（见后续待办）"，
但"待办"底下当时什么都没接。现在严重/重大事故**在报案那一刻**就通知在岗管理员
（`IncidentService::alertIfEscalated()`，去重键与轮询命令**刻意不同**：
"刚发生"与"过了时限还没人处理"是两件事，不该互相压制）。
告警失败会让报案失败吗？**不会** —— 报案人已经出过一次事了，不能因为平台内部通知写不进去让他再报一遍。

### ✅ 设备在线读时统一（本轮 · 2026-10-14）

`device_binding.online_status` 全仓**只有四处写它，每一处都写 `true`，没有任何地方写 `false`**
（`AgentController` 的握手/配对/心跳/取指令）。也就是说**一台三个月前就断线的设备，这一列至今写着"在线"**。

而它有**五个**读点（评审只列出四个，第五个是我核出来的）：

| 读点 | 改之前 | 改之后 |
|---|---|---|
| 我的设备（`DeviceController`） | 读粘滞列 | `isOnlineNow()` |
| 我的技能里的设备（`SkillController`） | 读粘滞列 | `isOnlineNow()` |
| 运营总览「在线设备数」（`OpsMetricsService`） | 读粘滞列 → 统计的是"曾经连过"的设备总数 | `scopeOnlineNow()` |
| 模拟网关（`MockAgentGateway`） | 读粘滞列 | `scopeOnlineNow()` |
| **兼容性校验（`CompatibilityService`）** | **硬编码 `return false`** —— 注释理由是"binding 未接在线心跳"，而心跳早就接了 → 界面**恒定**告诉用户"设备当前离线" | `$binding?->isOnlineNow()` |
| 轮询网关（`HttpPollAgentGateway`） | 自己写了一份 90 秒窗口 | 统一到 `DeviceBinding::ONLINE_WINDOW_SECONDS` |

**两套判据必然不一致**：同一台设备，"界面说在线、下发说离线"（或反过来）。
现已统一到 `DeviceBinding` 一处（常量 + 单条 `isOnlineNow()` + 集合 `scopeOnlineNow()`）。

**连带修正的行为**（这是好事）：下发链路本来就用 `isOnline()` 决定挂起（`pending_online`），
现在它读的是真实心跳 —— 给一台 90 秒没轮询的设备下发，会**如实挂起**而不是标成"已下发"等着永远没人取。
（取指令接口同时返回 `dispatching` 与 `pending_online`，所以任务不会卡死。）

**刻意不动的一处**：`IncidentService::traceFor()` 里的 `binding.online_status` **保持原样冻结**。
快照的契约是"记下当时库里写的是什么"，不是"现在是什么"。真信号（`last_online_at`）就在同一份快照里并排放着 ——
**平台不替历史下结论**。这条现在有测试锁着，免得将来被谁"顺手修好"。

### ⚠ 核验抓到的一个**会说谎的默认值**（已修）

`reconciliation.status` 的数据库默认值是 **`'matched'`（已平）**。
也就是说，任何一行新插入的对账记录，**在还没核对过任何东西的时候**就已经写着"已平" ——
对账的全部意义就是"两边能不能对上"，给一个默认成立的结论等于把这个功能变成装饰。

已改为 `pending`（迁移 `2026_10_14_000006`）。
**同类检查**：凡 status/result 的默认值**代表一个需要通过才能得到的结论**的列，默认都该是 pending/unchecked。
本轮做了这次清扫，又抓到一处（`skill_review.status` 默认 `visible`，迁移 `000007`），
并把"插一行、不给值、看落库"的行为级断言写进测试 —— 表结构断言防的是回退，行为断言防的是下一次。

## 二、能在代码里做完的（本文档负责的部分）

### ⚠ 开工前必须知道的三个**真漏洞**（勘察抓出来的，不是文档记载的）—— ✅ 三个都已修

| # | 漏洞 | 证据 | 危害 | 状态 |
|---|---|---|---|---|
| **B1** | **发布闸门缺失**：`Admin\Catalog\SkillController::publish()` 只检查 `assets->isEmpty()`，**不检查三层审核** | `SkillController.php:234`；而本该拦它的 `AuditService::isFullyApproved()` **全库零调用方** | 运营点一下"发布"，**未过审技能直接上架**。与 M2「垃圾被拒」判据直接冲突 | ✅ 已修：`ReviewGate` 策略化闸门 + 无绕过入口 |
| **B2** | **上传安全有两份实现**：Admin `storeAsset` 是**独立内联副本**，不走 `AssetUploadService`，**无 sha256 复核** | `Admin\...\SkillController.php:158-219` vs `Services\SkillSupply\AssetUploadService.php:38` | 两条入口安全强度不一致；一份修了另一份不会跟着修 | ✅ 已修：Admin 委托给同一个安全核，回归测试锁定 |
| **B3** | **`QualityService` 零调用方** —— `skill_quality` 表**永无写入** | 全库 grep 仅命中自身/模型/迁移 | 质量分级（qualified/good/featured）是**死代码**，前端拿不到分级 | ⬜ **未修**（见下方遗留）

> **修 B1 时连带解决的 B3'**：`isFullyApproved` 不仅零调用方，而且**写死"三层全过"** ——
> 直接接线会让**任何技能都发布不了**（L1 仿真器不存在）。现已改为按策略判定，
> `isFullyApproved` 委托给 `ReviewGate` —— **"过审"从此只有一处定义**。
>
> **处置方式值得记一笔**：闸门**没有**假装 L1 通过了。`config/skill_audit.php` 把
> `required_layers` 默认设为 `1,3`（不含 2），并在注释里写明**原因是仿真器未接入**，
> 界面上 L1 也显式显示为「未接入」，**不伪装成"通过"**。仿真器接入后改一个环境变量即可。
> 这是本项目一贯的「没查 ≠ 合规」原则的又一次应用。

**遗留（本轮未动，已记录在案）**：`QualityService` / `skill_quality` 仍是死代码 ——
质量分级要真正可用，得先有**真实数据源**（仿真得分 `sim_score`、安装成功率、
评分均值），这些依赖 L1 仿真器与足够的安装量。**在数据源不存在时强行接线，
只会得到一个永远输出同一个等级的分级器** —— 那比没有更糟。故留待数据具备时再做。
