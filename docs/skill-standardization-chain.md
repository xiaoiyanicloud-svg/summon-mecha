# 技能三端标准化链路设计（开发者上传 ↔ 平台转换 ↔ Agent 下发）

> 日期：2026-10-13 ｜ 直面问题：**开发者上传格式 / 平台 Agent / 厂家机型，三端如何标准化扣在一起，让"开发者传一次、各机型都能下"。**
> 依据：[agent-adaptation-plan.md](./agent-adaptation-plan.md)、[device-model-seed.md](./device-model-seed.md)、[skill-supply-plan.md](./skill-supply-plan.md)

---

## 0. 先承认缺了什么

之前我把三端**分开设计**了：
- 开发者端：`.skill`（manifest + motion/ + app/ + vendor/）
- 平台端：Agent、通道、导入器
- 机型端：device_model

**但没设计"中间那台转换机器"**——把**一份中立上传**变成**每机型能用的载体**。这才是"标准化"的关键。缺了它，就退化成"**开发者自己按每个机型传一份**"（你说的痛点）。

**本设计补上这一环，并把三端串成一条链路。**

---

## 1. 全链路：一次上传 → 多机型下发（fan-out）

```
┌─ 开发者上传端（标准化：传一份中立的）────────────────────┐
│  .skill = manifest.yaml + motion/(通用动作) + logic + 声明  │
└───────────────────┬──────────────────────────────────────┘
                    │ ①校验（格式/权限/安全）
                    ▼
┌─ 平台转换层（★核心：技能编译器 / 适配层）─────────────────┐
│  中立定义 ──► 按 target 机型编译成「载体」：               │
│    ├─► 宇树载体   (Docker 应用包 ARM64 + metadata.yaml)     │
│    ├─► 智元载体   (资源包 mcap + RPC 清单)                  │
│    └─► 众擎载体   (Runner 插件 / ROS2 包)                   │
│  动作重定向：通用动作 → 各机型关节空间（跨本体）            │
│  产出「一版本多载体」 → 落 skill_assets(carrier_type)       │
└───────────────────┬──────────────────────────────────────┘
                    │ ②审核 / 扫描 / 上架
                    ▼
┌─ 平台下发端（标准化：统一协议）───────────────────────────┐
│  deploy_task 状态机 + 签名 + 三通道选择                     │
│  统一协议：zhjj/{did}/cmd | evt（所有机型同一套指令/回报）  │
└───────────────────┬──────────────────────────────────────┘
                    │ ③按设备机型路由到对应载体 + 插件
                    ▼
┌─ Agent 下发端（一厂一插件，插件只负责"把载体装上"）────────┐
│  宇树插件：docker load + 起容器                             │
│  智元插件：拷 tmp + RPC 同步                                │
│  众擎插件：rsync + 机上运行                                 │
└───────────────────┬──────────────────────────────────────┘
                    ▼
                 各机型机器人
```

**一句话**：**开发者只对"中立定义"负责；机型差异全部由"平台转换层 + Agent 插件"吸收。**

---

## 2. 三端各自的"标准化点"

### 2.1 开发者上传端 —— 标准化为"中立技能定义"

开发者**不传**宇树/智元/众擎的格式，只传一份 **中立 `.skill`**：

```
skill/
  manifest.yaml        # 声明：名称/版本/权限/兼容机型/风险/适用 kind
  motion/              # 【通用动作数据】—— 平台负责重定向到各机型
    source.bvh | source.smplx | motion.macp
  logic/               # 【技能逻辑】—— 可选；用平台 SDK 写的统一逻辑
    skill.py / skill.cpp（调平台 SDK，不直接调厂商 API）
  assets/              # 音频/表情/贴图
  licenses/            # 授权
```

**关键**：开发者写逻辑时**调平台的统一 SDK**（不是宇树的 DDS、不是智元的 RPC）——**平台 SDK 屏蔽厂商差异**。这是"传一份"的前提。

### 2.2 平台转换层 —— ★核心（之前缺失的一环）

**职责**：把中立定义 → 编译成各目标机型的载体。

| 输入 | 转换 | 输出载体 |
|---|---|---|
| `motion/source.bvh`（通用动作） | **动作重定向**：映射到 G1 的 23 自由度 / A2 的 40 自由度 / PM01 的 24 自由度 | 各机型动作文件（宇树 CSV / 智元 mcap / 众擎轨迹） |
| `logic/skill.py`（平台 SDK） | **按机型打包** | 宇树=Docker 容器包；智元=资源+脚本；众擎=Runner 插件 |
| `manifest.compatibility` | 校验 + 生成 | 每机型 `device_model` 匹配规则 |

**产出**：一个技能版本 → **N 个载体**，落 `skill_assets`（`carrier_type` = 宇树/智元/众擎载体 + 通用动作）。⚠ **口径已降级（D-9，2026-10-16）**：`skill_build` 记的是**编排意图**，产物需外部重定向工具或人工回填，**平台侧当前没有生产者**（`BuildResult::success()` 全仓零调用点）。所以"一次上传、多机型可下"**目前不成立**——交付走的仍是开发者上传的那份文件。

**新增数据表 `skill_build`（编译记录）**：
```
id, skill_version_id, target(model_code/agent_type), status(pending/building/success/failed),
carrier_type, artifact_asset_id, retarget_conf JSON, build_log, error, built_at, timestamps
```

### 2.3 平台下发端 —— 标准化为"统一协议 + 统一状态机"

**不管什么机型，指令和回报是同一套**（见 agent-adaptation-plan §4）：
- 下行：`{task_id, operation, skill_id, version, package_url, package_hash, signature, ts}`
- 上行：`{task_id, phase, progress, error_code, ts}`

平台**不关心**宇树怎么装、智元怎么装——它只说"给这台设备装技能 X 的版本 Y"，**具体由对应插件执行**。

### 2.4 Agent 端 —— 标准化为"一厂一插件（只做载体落地）"

插件**只做一件事**：把平台给它的**该机型载体**装上去。
- 宇树插件：`docker load` + 起容器
- 智元插件：拷 `tmp` + RPC 同步
- 众擎插件：rsync + 机上运行

**插件不含业务逻辑、不做转换**——转换在平台层做完了。插件越薄越好。

## 3. 现实边界（必须诚实，不能过度承诺"全自动"）

| 技能类型 | 能否"传一次、多机型全自动" | 说明 |
|---|---|---|
| **纯动作（`kind=motion`）** | ✅ **基本可以** | 靠**动作重定向**（BVH/SMPL-X → 各本体关节）；重定向行业有成熟做法（众擎 GMR），但**不是 100% 无损**，高难度动作可能需人工调 |
| **带逻辑（`kind=app`）** | 🟠 **半自动** | 逻辑用**平台 SDK**写 → 平台可打包成各机型载体；但**运行时不同**（宇树 Docker / 智元资源 / 众擎插件），逻辑若用到机型特有硬件（如宇树某传感器），就**无法自动跨** |
| **厂商专有技能**（导入宇树的包） | ❌ **不能跨** | 宇树容器**物理上只跑宇树**（依赖 G1 DDS）→ 导入后**锁死该机型**（计划 §4.4.3 已定） |

**结论**：标准化是**分层的**——
- **动作层**：真正"一次编写、多机运行"（有限度）
- **逻辑层**：靠平台 SDK 尽量统一，但硬件相关部分需开发者按机型配
- **导入层**：厂商包不跨机型，只做该机型

> **别对外说"任何技能都能一次上传全机型运行"**——那是幻想。**能承诺的是：纯动作技能 + 用平台 SDK 写的逻辑，可一次上传、平台自动适配多机型。**

## 4. 数据模型如何支撑（与现计划对齐）

| 表 | 作用 |
|---|---|
| `skill_versions` | 中立定义（manifest_schema/source_format） |
| `skill_assets` | **一版本多载体**（carrier_type：宇树/智元/众擎/通用动作） |
| **`skill_build`（新增）** | **编译记录：中立定义 → 各机型载体的过程留痕** |
| `device_model` | 目标机型（重定向要用的自由度/关节定义） |
| `deploy_task` | 下发（统一协议，按机型路由载体） |

## 5. 与之前计划的差异（本次补强）

| 之前 | 现在 |
|---|---|
| 三端分开设计，没串起来 | **显式补"平台转换层"**，串成一条链路 |
| 开发者可能被要求按机型传 | **明确：开发者传一份中立定义**，机型差异平台吸收 |
| `skill_assets` 多载体但没说怎么来 | **`skill_build` 定义"多载体从哪来"** |
| Agent 插件职责模糊 | **插件只做载体落地**，转换在平台层 |

## 6. 待确认 / 需你拍板

1. **平台 SDK 要不要做？** —— 有了它，开发者才能"写一次逻辑、多机型跑"；没有它，带逻辑的技能就无法标准化。（**建议：P0 先只做"纯动作"标准化；SDK 化放 P1。**）
2. **动作重定向的自动化程度** —— 全自动（可能降质）vs 人工辅助（慢但准）？建议：**自动为主 + 高风险技能人工复核**。
3. **是否承诺"跨机型"** —— 建议只对 **`kind=motion`** 承诺，其余明确"按机型提供载体"。
